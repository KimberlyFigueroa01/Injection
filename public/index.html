¿Qué es SQL Injection?
OWASP Top 10 — A03:2021 Injection

SQL Injection ocurre cuando datos no confiables del usuario se envían a un intérprete como parte de un comando o consulta. Los datos hostiles del atacante pueden engañar al intérprete para que ejecute comandos no deseados o acceda a datos sin autorización.

🔴
Código Vulnerable (Concatenación):
SELECT * FROM users WHERE username = '${username}' AND password = '${password}'
🟢
Código Seguro (Prepared Statement):
SELECT * FROM users WHERE username = ? AND password = ?
🧹
Sanitización vs Parametrización
Dos capas de defensa complementarias

La parametrización separa el código SQL de los datos del usuario, evitando que los datos se interpreten como código. La sanitización limpia el input antes de usarlo, eliminando caracteres que podrían ser peligrosos incluso dentro de un contexto parametrizado (como los wildcards % y _ en cláusulas LIKE).

⚠️
Solo parametrización (insuficiente para LIKE):
Input: % → parámetro: %% → retorna TODOS los registros, igual que sin protección.
🟢
Sanitización + Parametrización (defensa en profundidad):
Input: % → sanitizado: (vacío — bloqueado) → se rechaza antes de llegar a la BD.
💉
¿Cómo funciona el ataque?
Paso a paso
  1. El atacante ingresa un payload malicioso en el campo de usuario: admin' --
  2. La aplicación concatena el input directamente en la consulta SQL sin sanitizar
  3. La consulta resultante es: SELECT * FROM users WHERE username = 'admin' --' AND password = 'x'
  4. El -- comenta el resto de la consulta, eliminando la verificación de contraseña
  5. El atacante obtiene acceso como administrador sin conocer la contraseña
🛡️
Mitigaciones Recomendadas
Buenas prácticas de seguridad
  1. Prepared Statements (Consultas Parametrizadas): Separar el código SQL de los datos del usuario
  2. ORM (Object-Relational Mapping): Usar herramientas como Sequelize, Prisma o SQLAlchemy que generan consultas seguras
  3. Validación de Entrada: Verificar tipo, longitud y formato de todos los datos del usuario
  4. Principio de Mínimo Privilegio: La cuenta de BD solo debe tener los permisos estrictamente necesarios
  5. WAF (Web Application Firewall): Filtrar patrones de inyección conocidos como capa adicional
  6. Escapar Caracteres Especiales: Como última línea de defensa, escapar caracteres como ' " ; --
☠️
Riesgos Asociados
Impacto potencial de la vulnerabilidad
⚠️
Confidencialidad: Exposición total de la base de datos (usuarios, contraseñas, datos sensibles)
Integridad: Modificación o eliminación de datos (DROP TABLE, UPDATE)
Disponibilidad: Denegación de servicio o destrucción de la base de datos
Autenticación: Bypass completo del sistema de autenticación
Escalación: Posible ejecución de comandos en el servidor (xp_cmdshell en SQL Server)
⚖️
Comparación: Vulnerable vs Seguro
Diferencias clave en el código

🔴 INSEGURO Concatenación

// ⚠️ Node.js — Vulnerable const query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`; db.prepare(query).all(); // El input del usuario se INSERTA // directamente en la cadena SQL
# ⚠️ Python Flask — Vulnerable query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'" cursor.execute(query)
// ⚠️ PHP — Vulnerable $query = "SELECT * FROM users WHERE username = '$user' AND password = '$pass'"; mysqli_query($conn, $query);

🟢 SEGURO Parametrizado

// ✅ Node.js — Seguro const query = `SELECT * FROM users WHERE username = ? AND password = ?`; db.prepare(query).all( username, password ); // Los valores se pasan SEPARADOS
# ✅ Python Flask — Seguro query = "SELECT * FROM users WHERE username = %s AND password = %s" cursor.execute(query, (username, password))
// ✅ PHP — Seguro (PDO) $stmt = $pdo->prepare( "SELECT * FROM users WHERE username = ? AND password = ?"); $stmt->execute( [$user, $pass]);
